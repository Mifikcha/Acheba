# Источники данных

[Сериализация](https://www.google.com/url?q=https%3A%2F%2Fru.wikipedia.org%2Fwiki%2F%D0%A1%D0%B5%D1%80%D0%B8%D0%B0%D0%BB%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F) — это преобразование объекта или дерева объектов в какой-либо формат, чтобы потом эти объекты можно было восстановить. Обратной к операции сериализации является [десериализация](https://www.google.com/url?q=https%3A%2F%2Fru.wikipedia.org%2Fwiki%2F%D0%94%D0%B5%D1%81%D0%B5%D1%80%D0%B8%D0%B0%D0%BB%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F) — восстановление структур и объектов из сериализованной строки или последовательности байтов.

На данный момент одними из основных форматов хранения данных являются _[JSON](https://www.google.com/url?q=https%3A%2F%2Fru.wikipedia.org%2Fwiki%2FJSON), [CSV](https://www.google.com/url?q=https%3A%2F%2Fru.wikipedia.org%2Fwiki%2FCSV), [XML](https://www.google.com/url?q=https%3A%2F%2Fru.wikipedia.org%2Fwiki%2FXML), [YAML](https://www.google.com/url?q=https%3A%2F%2Fru.wikipedia.org%2Fwiki%2FYAML)_.

### Требования
1. Окончание строк в стиле MS-DOS, символы (Carriage Return / Line Feed). Или ‘\n’, ‘\r’
2. Необязательная строка заголовка
3. каждая строка (запись) должна содержать одинаковое количество полей
4. поле может быть заключено в двойные кавычки.
5. если поле содержит зарезервированные символы, то это поле должно быть заключено в двойные кавычки
6. символ двойной кавычки в поле должен быть удвоен (своего рода экранирование)

### Применение
1. Выгрузки логов (табличный формат)
2. Выгрузка базы данных
3. Любая ситуация, когда данные имеют табличный формат и не хочется заморачиваться с более сложными форматами. Т.к. очень широкий спектр инструментов работы с ним

## JSON (Java Script Object Notation)

По сути имеет структуру словаря

**Типы данных:**
- JSON-объект
- Массив
- Число (целое или вещественное)
- Литералы true, false и null
- Строка

### Пример

JSON-объект — это неупорядоченное множество пар «ключ:значение»

```json
{
  "query": "Виктор Иван",
  "count": 7,
  "marks": [5, 5, 4, 5, 2, 1],
  "has_phone": false,
  "info": {"married": true, "address": "Moscov"}
}
```

Основные функции, которые понадобятся при работе с JSON:

- **dump(объект, файл, ensure_ascii, *args, **kwargs)** - сериализует объект в JSON формат и возвращает его. Для работы с кириллицей используем флаг _ensure_ascii=False_
- **load(файл, *args, **kwargs)** - десериализует JSON-строку в Python объект и вовращает его
- Помимо этого есть **dumps(объект, *args, **kwargs)** и **loads(строка, *args, **kwargs)**, которые позволяют переводить объект в JSON-строку и обратно, без последующего сохранения в файл

### Примечания

Заметим, что соответствие при сериализации-десериализации не всегда взаимооднозначно.
Это значит что если вы кодируете объект, а затем декодируете его, вы можете не получить тот же объект назад. Это можно представить как своего рода телепортацию: молекулы тела распадаются в точке А и собираются в точке Б. Будет ли это тело прежним?

Например, сохраняя tuple в Python мы получаем array в JSON. Однако, переводя JSON array обратно в Python объект, получаем list. Таким образом, tuple Python после сериализации-десериализации превращается в list Python.

Также следует упомянуть, что не все объекты в Python могут быть сериализованы. Примером такого объекта является комплексное число (класс complex)

```python
# Пример: попытка сериализации неподдерживаемого объекта
import json
try:
  s = json.dumps(9 + 5j)
  print(s)
except TypeError as e:
  print(e.args[0]) # вывод сообщения об ошибке
```

```shell
Object of type complex is not JSON serializable
```

Также не поддерживается сериализация пользовательских типов

```python
import json

class Elf:
    def __init__(self, level, hp=100):
        self.level = level
        self.hp = hp

elf = Elf(level=80)
try:
  s = json.dumps(elf)
  print(s)
except TypeError as e:
  print(e.args[0])
```

```shell
Object of type Elf is not JSON serializable
```

!! Посколько сериализации сложных объектов Python не поддерживается по умолчанию, чтобы записать их в JSON, вам необходимо либо превратить его в набор базовых объектов, либо написать свой encoder:

```python
#Пример: Упрощение структур
#Рассмотрим пример сериализации комплексного числа
import json

def encode_complex(z):
    if isinstance(z, complex):
        return (z.real, z.imag)
    else:
        type_name = z.__class__.__name__
        raise TypeError(f"Object of type '{type_name}' is not JSON serializable")

print(json.dumps(9 + 5j, default=encode_complex))
```

```shell
[9.0, 5.0]
```

```python
#Пример: Написание Encoder
import json

class ComplexEncoder(json.JSONEncoder):
    def default(self, z):
        if isinstance(z, complex):
            return (z.real, z.imag)
        else:
            super().default(self, z)


#Пример 1
print(json.dumps(2 + 5j, cls=ComplexEncoder))

#Пример 2
encoder = ComplexEncoder()
print(encoder.encode(3 + 6j))
```

```shell
[2.0, 5.0] 
[3.0, 6.0]
```
### Требования

1. Переносы строк не обязательны
2. Ключ всегда строка (в отличие от словаря)
3. Между ключом и значением “:”
4. Между парами “ключ”:значение “,”
5. Запятую в конце не ставить
6. Соблюдать последовательность открытия и закрытия `{}` и `[]`

### Применение

1. REST API
2. Передача данных внутри между front и back
3. Конфигурационные файлы

Редактирование XML

```python
from lxml import etree
from lxml.etree import Element, ElementTree

xml_str = """<parent>
        <data name="key_first" xml:space="preserve">
            <value>Text 1</value>
        </data>
        <data name="key_second" xml:space="preserve">
            <value>Text 2</value>
        </data>
        <data name="key_third" xml:space="preserve">
            <value>Text 3</value>
        </data>
</parent>"""

root = etree.fromstring(xml_str)
tree = ElementTree(root)
print(type(root), type(tree))
data_second = root.find(".//data[@name='key_second']") # поиск с помощью XPATH
root.remove(data_second) # удаление найденного элемента

new_data = Element("data") # создание нового тега <data>
new_data.set("name", "key_new")

sub_element = Element("value")
sub_element.text = 'Text New'

new_data.append(sub_element) # добавляет <value /> тег внутрь <data>
root.append(new_data) # добавляет созданный data последним элементом в <parent>

etree.dump(root)
```

## YAML (Yet Another Markup Language)

Ещё один язык разметки
Переименован в Ain’t Markup Language - не язык разметки

**Типы данных:**
- строки, числа, логический, дата/время
- последовательности, словари

### Поддерживает

- комментарии
- наследование
- шаблоны
- якоря

### Примечания

Так как YAML — это расширенный JSON, то мы можем писать YAML-файл в JSON-формате, и он будет работать.

Согласно YAML спецификации, порядок ключей в словарях не сохраняется (например, когда используем safe_load). Только метод round_trip_load сохраняет порядок ключей (комментариев и т.д.)

Возможности YAML-а покоряют при его сравнении с JSON. Но если у вас довольно простой конфиг в пару-тройку строк, то нет смысла усложнять и использовать дополнительные возможности YAML, лучше выбрать JSON. А если же у вас довольно большой и витиеватый файл, то тут однозначно стоит рассмотреть YAML.


## Pickle (python only)

консервация
библиотека, предоставляющая инструментарий для наиболее простой и эффективной сериализации сложных Python-объектов в бинарном виде. В отличие от вышеприведённых форматов, Pickle поддерживается только Python. Это значит, что декодировать этот формат не получится в других языках программирования. Из-за внутреннего устройства этого формата, десериализация непроверенных данных может привести к выполнению произвольного вредоносного кода

**Типы данных:**
- None, True, False
- Строки (обычные или Юникод
- Стандартные числовые типы данных
- Словари, списки, кортежи
- Функции
- Классы

### Плюсы

- максимально прост в использовании
- поддерживает пользовательские структуры и классы
- не требует какого-либо парсинга

### Минусы

- небезопасен ([статья]([https://habr.com/ru/companies/otus/articles/353480/](https://habr.com/ru/companies/otus/articles/353480/)))
- зависим от версии и протокола
- не умеет “расконсервировать” пользовательские классы, если они не заданы перед “расконсервацией”

### Пример

Основные функции, которые понадобятся при работе с pickle:

- **dump(объект, файл, *args, **kwargs)** - сериализует объект в pickle байткод.
- **load(файл, *args, **kwargs)** - десериализует pickle-файл в Python объект.
- Помимо этого есть **dumps(объект, *args, **kwargs)** и **loads(строка, *args, **kwargs)**, которые позволяют переводить объект в pickle байткод и обратно, без последующего сохранения в файл (по аналогии с JSON)

```python
import pickle

original = { 'a': 0, 'b': [1, 2, 3] }

pickled = pickle.dumps(original)
print("Сериализованный объект выглядит так:")
print(pickled)
# преобразовать обратно в идентичный объект
identical = pickle.loads(pickled)
print("Десериализованный Pickle-объект:")
print(identical)
assert original == identical
```

```shell
Сериализованный объект выглядит так:
b'\x80\x04\x95\x19\x00\x00\x00\x00\x00\x00\x00}\x94(\x8c\x01a\x94K\x00\x8c\x01b\x94]\x94(K\x01K\x02K\x03eu.'
Десериализованный Pickle-объект:
{'a': 0, 'b': [1, 2, 3]}
```

```python
csv = pd.read_csv('data.csv')
```

## HDF/HDF5 (Hierarchical Data Format) 

HDF/[HDF5](https://www.hdfgroup.org/solutions/hdf5/) (Hierarchical Data Format) - иерархический формат данных

==Разработан== Национальным центром суперкомпьютерных приложений

==Поддерживается== open source организацией HDF Group

Поддерживает API: Java, Python, R, Julia, Scilab, Octave, Matlab, Mathematica, IDK

### Версии формата:

1. HDF4 (поддерживается)  
Поддерживает модели данных:  
- многомерные массивы  
- таблицы  
- растровые изображения

2. HDF5 (актуальная версия)  
Поддерживает иерархию 2 типов:  
- DataSets - наборы данных, многомерные массивы объектов одного типа  
- Groups - группы являются контейнерами для наборов данных и других групп

### Особенности

1. Поддерживает n-мерные наборы данных, и каждый элемент в наборе данных сам по себе может быть сложным объектом
2. Является портативным, не привязанным к поставщику и представляет собой самоописывающийся формат файлов, что означает, что все данные и метаданные могут передаваться в одном файле.
3. Работает на различных вычислительных платформах, от ноутбуков до систем с массовым параллелизмом, и реализует высокоуровневый API с интерфейсами C, C++, Fortran и Java. Имеет большую экосистему, насчитывающую более 700 проектов Github.
4. Высокопроизводительный ввод-вывод с богатым набором интегрированных функций производительности, которые позволяют оптимизировать время доступа и пространство хранения
5. Нет ограничений на количество или размер объектов данных в коллекции, что обеспечивает большую гибкость при работе с большими данными
6. Позволяет хранить метаданные вместе с данными, оптимизируя жизненные циклы и конвейеры данных

### Принцип

Файл HDF5 представляется пользователю как ориентированный граф.
Узлы этого графа — это объекты HDF5 более высокого уровня, предоставляемые API-интерфейсами HDF5:
- Groups
- DataSets

На самом низком уровне, когда информация фактически записывается на диск, файл HDF5 состоит из следующих объектов:
- Superblock, B-tree nodes, Heap blocks,
- Object headers, Object data, Free space

Библиотека HDF5 использует объекты низкого уровня для представления объектов более высокого уровня, которые затем представляются пользователю или приложениям через API
#### Структура

Подробно про [модель](https://bitbucket.hdfgroup.org/pages/HDFFV/hdf5doc/master/browse/html/UG/HDF5_Users_Guide-Responsive%20HTML5/index.html) формата

![[структура_hdf5.png]]

### Описание схемы формата

Группа — это заголовок объекта, содержащий сообщение, указывающее на локальную кучу (для хранения ссылок на объекты в группе) и на B-дерево (которое индексирует ссылки).

### Пример

Набор данных — заголовок объекта, который содержит сообщения, описывающие тип данных, пространство данных, макет, фильтры, внешние файлы, значение заполнения и другие элементы.

Причем сообщение макета указывает либо на фрагмент необработанных данных, либо на B-дерево, указывающее на необработанные данные, фрагменты данных.

```python
import time
import numpy as np
import h5py
import os

arr = np.random.randn(1000)

with h5py.File('groups.hdf5', 'w') as f:
    g = f.create_group('Base_Group')
    d = g.create_dataset('default', data=arr)

    g.attrs['Date'] = time.time()
    g.attrs['User'] = 'Me'

    d.attrs['OS'] = os.name

    metadata = {'Date': time.time(),
                'User': 'Me',
                'OS': os.name,}

    f.attrs.update(metadata)

    for k in g.attrs.keys():
        print('groups key')
        print('{} => {}'.format(k, g.attrs[k]))

    for j in d.attrs.keys():
        print('dataset key')
        print('{} => {}'.format(j, d.attrs[j]))

    for m in f.attrs.keys():
        print('file key')
        print('{} => {}'.format(m, f.attrs[m]))
```

### Еще несколько акцентов

- автоматический подсчёт контрольных сумм для проверки целостности данных
- несколько способов сжатия данных

### Минусы

- заявлен, как формат для Big Data, но по факту проигрывает многим Big Data форматам
- небольшие файлы занимают неоправданно много места
- есть дописывание в существующий файл, но существуют риски всё сломать

## ORC (Optimized Row Columnar)

Оптимизированный строково-столбчатый формат файлов

### Преимущества

1. Один файл на выходе каждой задачи, что уменьшает нагрузку на NameNode (узел имен)
2. Поддержка типов данных Hive, включая DateTime, десятичные и сложные типы данных (struct, list, map и union)
3. Одновременное считывание одного и того же файла разными процессами RecordReader
4. Оценка максимально возможного выделения памяти на процессы чтения/ записи по информации в футере файла
5. Метаданные сохраняются в бинарном формате сериализации Protocol Buffers, который позволяет добавлять и удалять поля

### Модель формата

![[orc_model_fromat.png]]

### Особенности

1. ORC хранит коллекции строк в одном файле, а внутри коллекции строчные данные хранятся в столбчатом формате
2. Хранит группы строк, которые называются полосами (stripes) и вспомогательную информацию в футере файла. Postscript в конце файла содержит параметры сжатия и размер сжатого футера
3. По умолчанию размер полосы составляет 250 МБ
4. Индексы ORC используются только для выбора полос и групп строк, а не для ответа на запросы
5. В футере файла записан список полос в файле, количество строк на полосу и тип данных каждого столбца. Там же записано результирующее значение count, min, max и sum по каждому столбцу.
6. Футер полосы содержит каталог местоположений потока
7. Строчные данные используются при сканировании таблиц
8. Индексные данные включают минимальные и максимальные значения для каждого столбца

## AVRO

строковый, формат хранения данных в Hadoop

### Особенности

1. Он хранит схему в формате JSON, облегчая ее чтение и интерпретацию любой программой
2. Данные лежат в двоичном формате, компактно и эффективно
3. Система сериализации Avro нейтральна к языку. Файлы можно обрабатывать разными языками, в настоящее время это C, C++, C#, Java, Python и Ruby
4. Надежная поддержка схем данных, которые изменяются с течением времени (удаление, добавление, изменение полей)

Avro поддерживает разнообразные структуры данных.

Например, можно создать запись, которая содержит массив, перечислимый тип и подзапись

![[avro.png]]

### Поддержка типов

- примитивные (null, Boolean, int, long, float, double, string, bytes, fixed);
- сложные составные (union, recod, enum, array, map);
- логические (decimal, date, time-millis, time-micros, timestamp-millis, timestamp-micros, uuid).

### Достоинства

1. Высокая скорость записи информации, что особенно важно в потоковых Big Data системах – именно поэтому Авро очень активно применяется в Apache Kafka и корпоративных озерах данных
2. Формат отлично подходит для ETL-хранилищ и витрин данных, где требуется чтение всех полей записи, а не избирательно по столбцам, как в колоночно-ориентированных форматах

### Недостатки

1. Пониженная скорость чтения информации, поскольку требуется читать все поля записи;
2. Меньшая производительность при выполнении избирательных запросов;
3. Больший расход дискового пространства для хранения данных

### Сфера применения

Идеально подходит для записи в посадочную (переходную) зону озера данных (data lake)

Почему?

1. Любое изменение исходной схемы легко обрабатывается (эволюция схемы)
2. Данные из этой зоны обычно считываются целиком и формат на основе строк в этом случае более эффективен
3. Нижестоящие системы могут легко извлекать таблицы схем из файлов — не нужно хранить схемы отдельно во внешнем мета-хранилище

## PARQUET

бинарный, колоночно-ориентированный формат хранения данных, является независимым от языка

## Особенности

1. В каждой колонке данные должны быть строго одного тип
2. Можно считывать не целиком весь файл, а только одну колонку
### Введем понятия

1. Группа строк (row group): логическое горизонтальное разбиение данных на строки. Группа строк состоит из фрагмента каждого столбца в наборе данных
2. Фрагмент столбца (column chunk): фрагмент конкретного столбца. Эти фрагменты столбцов живут в определенной группе строк и гарантированно будут смежными в файле
3. Страница (page): фрагменты столбцов делятся на страницы, записанные друг за другом. У страниц общий заголовок, так что при чтении можно пропустить ненужные

### Общее представление

![[parquet.png]]

- Header: содержит число PAR1 (4 байта), которое идентифицирует файл как файл формата Parquet

1. Footer. Метаданные
	- Метаданные файла содержат стартовые координаты метаданных каждого столбца.
	- При чтении нужно сначала прочитать метаданные файла, чтобы найти все интересующие фрагменты столбцов.
	- Затем фрагменты столбцов следует читать последовательно. Еще метаданные включают версию формата, схему и любые дополнительные пары ключ-значение
1. Footer. Длина метаданных (4 байта)
2. Волшебное число PAR1 (4 байта)

## Avro vs Parquet

1. Avro — формат хранения по строкам, тогда как Parquet хранит данные по столбцам.
2. Parquet лучше подходит для аналитических запросов, то есть операции чтения и запрос данных гораздо эффективнее, чем запись
3. Операции записи в Avro выполняются эффективнее, чем в Parquet
4. Avro более зрело работает с эволюцией схем. Parquet поддерживает только добавление схемы, а в Avro реализована многофункциональная эволюция, то есть добавление или изменение столбцов
5. Parquet идеально подходит для запроса подмножества столбцов в многоколоночной таблице. Avro подходит для операций ETL, где мы запрашиваем все столбцы.

## ORC vs Parquet

1. Parquet лучше хранит вложенные данные
2. ORC лучше сжимает данные
3. ORC поддерживает свойства ACID (атомарность, непротиворечивость, изоляция, устойчивость)
4. ORC лучше в проталкивании [предикатов](https://habr.com/ru/companies/lsfusion/articles/463095/) (predicate pushdown)
