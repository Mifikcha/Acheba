# Архитектура базы знаний Obsidian

## Цель

Развернуть в корне существующего Obsidian Vault переносимую базу знаний уровня Level 2 с локальным семантическим поиском Level 3. Существующие заметки остаются на месте. Markdown, YAML frontmatter и Obsidian-ссылки являются источником истины; поисковый индекс можно удалить и построить заново.

## Структура

В корне создаются каталоги `00_System`–`05_Semantic_Index` из пользовательской спецификации. В `00_System/TEMPLATES` хранятся шаблоны проекта, решения, инсайта, анализа, встречи, концепции и источника. В `01_Projects/example-project` создаётся демонстрационный проект со всеми обязательными файлами и подкаталогами. В `04_Indexes` находятся навигационные индексы.

Существующие каталоги и заметки не перемещаются автоматически: массовая миграция без ручной классификации могла бы разрушить текущую навигацию.

## Инструкции и рабочий цикл

`00_System/AGENT_INSTRUCTIONS.md` описывает:

- маршрутизацию новых материалов;
- порядок восстановления контекста проекта;
- разделение истории, решений, инсайтов и неудач;
- обновление индексов и семантического слоя;
- правила качества, архивирования и защиты секретов.

`00_System/INDEX.md` служит главной точкой входа, `GLOSSARY.md` фиксирует термины. Демонстрационный проект показывает полный цикл: состояние, история, принятое решение, инсайт, задачи и ссылки.

## Семантический индекс

Python CLI в `05_Semantic_Index` предоставляет команды:

- `index` — найти содержательные Markdown-файлы, разобрать frontmatter, разбить текст по заголовкам, вычислить стабильные идентификаторы и обновить только изменившиеся чанки;
- `search` — выполнить лексический и векторный поиск, применить фильтры и объединить оценки;
- `validate` — проверить дубликаты ID, обязательный frontmatter и разрешимость wiki-ссылок.

Основной backend embeddings — `sentence-transformers`, но он используется только при уже доступной библиотеке и локальной модели. CLI не скачивает модель без явного действия пользователя. Если backend недоступен, автоматически применяется полностью офлайн детерминированный hashing-векторизатор. Выбранный backend, модель, размерность, время обновления и статистика сохраняются в `manifest.json`.

Hashing fallback строит нормированные векторы по словесным и символьным признакам. Он уступает трансформеру в семантике, но сохраняет работоспособность, повторяемость и возможность гибридного поиска без внешних зависимостей.

## Данные и инкрементальность

`chunks.jsonl` содержит метаданные и текст чанков в формате пользовательской спецификации. Векторное представление хранится локально в `index/` и связывается с `chunk_id`. `content_hash` определяет изменение чанка; отсутствующие исходники удаляются из индекса. Стабильный `chunk_id` зависит от постоянного ID заметки и логического положения раздела, а не от времени запуска.

Исключаются `.obsidian`, `.git`, `AGENTS`, шаблоны, архивы, корзина, служебные каталоги, `.env`, сам семантический индекс и явно технические файлы. Markdown без frontmatter не ломает индексирование существующего Vault: ему назначается устойчивый производный `note_id`, но валидатор отдельно сообщает о нарушении для содержательных заметок новой архитектуры.

## Поиск

Лексическая оценка учитывает совпадения токенов и имён. Векторная оценка использует cosine similarity. Итоговый рейтинг объединяет обе оценки и повышает точные совпадения. Поддерживаются фильтры по проекту, типу и диапазону дат.

Каждый результат показывает название заметки, путь, заголовок, релевантный фрагмент, причину совпадения, Obsidian-ссылку и уверенность. CLI явно предупреждает, что фрагмент не заменяет полный контекст исходной заметки.

## Обработка ошибок

- Повреждённый frontmatter не останавливает весь проход: ошибка попадает в отчёт проверки.
- Недоступный transformer backend приводит к fallback, а не к отказу.
- Повреждённый или несовместимый индекс перестраивается из Markdown.
- Файлы с ошибкой чтения перечисляются в журнале и не удаляют ранее корректные данные до успешного завершения прохода.
- Запись индекса выполняется через временные файлы с последующей заменой.

## Проверка

Реализация ведётся тестами на временном Vault. Тесты покрывают:

- разбор frontmatter и чанкинг по заголовкам;
- стабильность ID и инкрементальное обновление;
- удаление устаревших чанков;
- fallback embeddings;
- гибридный поиск и фильтры;
- проверку дубликатов ID, frontmatter и wiki-ссылок;
- полный цикл индексирования и поиска демонстрационного проекта.

Финальная проверка включает запуск модульных тестов, построение реального индекса, тестовый запрос и `validate`.

## Границы

В первую версию не входят GUI, облачная синхронизация, автоматическая классификация всех существующих заметок и загрузка моделей из сети. Эти возможности можно добавить позже, не меняя Markdown-слой.
